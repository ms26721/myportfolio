Task 2: Showcase of Artefacts

Advanced Object-Oriented Design & Programming · Capstone Project: End of Module Reflective Portfolio

The artefacts below come from weekly exercises and the Capstone Project. Code is abridged for length.

Artefact 1: Thread-safe ticket ID generator (coding exercise)

import threading

class TicketIdGenerator:
    def __init__(self, start: int = 1000):
        self._next = start
        self._lock = threading.Lock()

    def next_id(self) -> int:
        with self._lock:  # critical section
            current = self._next
            self._next += 1
            return current

Without the lock, a stress test running many threads concurrently produced duplicate IDs. Encapsulating both the counter and the lock means callers cannot bypass synchronisation, and a ThreadPoolExecutor-based test now verifies uniqueness.

Artefact 2: Strategy pattern – pricing and triage rules

class PricingStrategy(ABC):
    @abstractmethod
    def price(self, ticket) -> float: ...

class StandardPricing(PricingStrategy):
    def price(self, t): return 40.0 * t.hours

class PremiumSLAPricing(PricingStrategy):
    def price(self, t): return 55.0 * t.hours * (1.5 if t.urgent else 1.0)

class Quote:
    def __init__(self, strategy: PricingStrategy): self.strategy = strategy
    def total(self, ticket): return self.strategy.price(ticket)

Why chosen: pricing rules and AI triage logic differed by client contract and changed frequently; Strategy replaced a growing if/elif chain. Benefit: each rule is unit-tested in isolation and new rules are added without editing Quote. The same structure lets a rule-based triager and an ML triager be swapped at runtime.

Artefact 3: Decorator pattern – logging and security layers

class ServiceDecorator(TicketService):
    def __init__(self, inner: TicketService): self._inner = inner

class RequireRole(ServiceDecorator):
    def __init__(self, inner, role): super().__init__(inner); self._role = role

    def submit(self, user, ticket):
        if self._role not in user.roles: raise PermissionError("denied")
        return self._inner.submit(user, ticket)

class AuditLogging(ServiceDecorator):
    def submit(self, user, ticket):
        log.info("submit by %s", user.id)
        return self._inner.submit(user, ticket)

service = AuditLogging(RequireRole(CoreTicketService(), "agent"))

Why chosen: logging and authorisation are cross-cutting concerns that should not live inside business logic. Benefit: layers are composable and reorderable, and the core service is tested without security or logging noise.

Artefact 4: Visitor pattern – analytics and reporting

class ReportVisitor(ABC):
    @abstractmethod
    def visit_ticket(self, t): ...
    @abstractmethod
    def visit_device(self, d): ...

class Ticket:
    def accept(self, v): return v.visit_ticket(self)

class SLABreachReport(ReportVisitor):
    def __init__(self): self.breaches = 0
    def visit_ticket(self, t): self.breaches += t.resolution_hrs > t.sla_hrs
    def visit_device(self, d): pass

Why chosen: the ticket/device structure was stable, but reporting requirements changed often. Benefit: analytics are separated from domain objects, and a new report is simply a new class. The trade-off is that adding a new element type forces changes to every visitor.

Artefact 5: Abstract Factory – switching AI service providers

class AIServiceFactory(ABC):
    @abstractmethod
    def classifier(self) -> Classifier: ...
    @abstractmethod
    def summariser(self) -> Summariser: ...

class CloudAIFactory(AIServiceFactory):
    def classifier(self): return CloudClassifier(os.environ["AI_KEY"])
    def summariser(self): return CloudSummariser()

class LocalAIFactory(AIServiceFactory):
    def classifier(self): return registry.get("triage", version="v3")
    def summariser(self): return LocalSummariser()

factory = LocalAIFactory() if config.data_residency else CloudAIFactory()

Why chosen: some clients require data to stay on-premises, and components from different providers must not be mixed. Benefit: vendor independence, guaranteed family consistency, and a FakeAIFactory for tests.

2.6 Testing: mocking and AI-driven testing

from unittest.mock import Mock

def test_urgent_ticket_routed_to_priority_queue():
    clf = Mock(spec=Classifier)
    clf.predict.return_value = "urgent"
    assert TicketRouter(clf).route(Ticket("Server down")) == "priority"
    clf.predict.assert_called_once()

def test_fallback_when_model_times_out():
    clf = Mock(spec=Classifier); clf.predict.side_effect = TimeoutError
    assert TicketRouter(clf).route(Ticket("Printer jam")) == "standard"

Using pytest and unittest.mock, I isolated classes from their collaborators; spec= ensures each mock honours the real interface. AI-dependent components were tested without live models or APIs: mocks returned deterministic labels and simulated failures via side_effect, making tests fast, free and repeatable.

I also reflected on AI-assisted testing tools. An AI coding assistant was useful for test-case generation, quickly drafting boundary tests for pricing rules. Combined with property-based testing (Hypothesis), it supported edge-case discovery, surfacing inputs such as empty descriptions and zero-hour tickets that I had not considered. Generated tests, once reviewed, were added to the regression suite run on every commit. However, several suggestions merely asserted current behaviour rather than intended behaviour, or duplicated existing tests. I therefore treated AI as a support for OO quality, not a replacement for engineering judgement: I decided what “correct” meant, and the tools helped me check it.

2.7 Capstone Project: SmartDesk

  • Patterns and scalable architecture: Strategy and Abstract Factory made AI and pricing behaviour pluggable; Decorator kept cross-cutting concerns at the edges; Visitor allowed reporting to grow independently.

  • Testing for robustness: mock-based unit tests, integration tests per factory, a concurrency stress test and continuous regression testing gave confidence when refactoring.

  • AI-readiness at design level: models sit behind interfaces, are versioned in a registry and created through factories, with a rule-based fallback strategy, so new models can be adopted without redesign.

2.8 Critical commentary on artefacts

Artefact OO principles and techniques Challenges and how I overcame them
Thread-safe generator Encapsulation, information hiding, context manager Intermittent race was hard to reproduce; I built a stress test first, then added the lock.
Strategy Polymorphism, Dependency Inversion, Open/Closed Deciding who selects the strategy; a small factory driven by contract configuration solved this.
Decorator Composition, Single Responsibility, Liskov Substitution Wrapping order changed behaviour; I documented the intended order and tested it.
Visitor Double dispatch, separation of concerns Python lacks method overloading and double dispatch was initially confusing; explicit visit_x names and a diagram clarified it.
Abstract Factory Abstraction, Dependency Inversion, family consistency Providers had unequal capabilities; I designed to a common interface with optional capability checks.
Mock-based tests Dependency injection, test doubles Over-mocking made tests brittle; I limited mocks to architectural boundaries.

2.9 Trade-offs and critical reflection

Pattern selection trade-offs: each pattern resolved one problem while creating another. Visitor eases adding operations but makes adding element types costly; Decorator adds flexibility but deep wrapper chains complicate debugging. In Python, a simple function can often replace a Strategy class, so I reserved full classes for strategies that hold state or configuration.

Testing complexity: abstraction improved testability, but more interfaces meant more test doubles and fixtures to maintain. Concurrency and AI behaviour were the hardest to test deterministically, which I addressed with controlled mocks and repeated stress runs.

Abstraction vs over-engineering: I initially created an Abstract Factory for notification channels with only one implementation. Applying YAGNI and the “rule of three”, I removed it. My working rule became: introduce an abstraction when there is a real second variant or a clear testing need, not in anticipation.
