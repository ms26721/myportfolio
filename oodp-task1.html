Task 1: Summary of Key Learning Outcomes

Advanced Object-Oriented Design & Programming · Capstone Project: End of Module Reflective Portfolio

1.1 Secure coding practices

Early in the module I treated security as something added at the end. The secure-coding units changed that: I now see security as a design property. I applied input validation at trust boundaries, least privilege, and encapsulation that keeps sensitive state private behind validated methods. I also learned that concurrency faults are security faults, because race conditions can corrupt state or expose data.

Practical evidence: in SmartDesk every incoming ticket passes through a validation layer that rejects malformed or oversized payloads before they reach domain objects, database access uses parameterised queries, and API keys are loaded from environment variables rather than hard-coded. In the threading exercise (Artefact 1) I protected a shared counter with a lock after first reproducing the race condition under load.

1.2 Advanced object-oriented principles

I deepened my use of abstraction, encapsulation, inheritance and polymorphism, and learned to treat the SOLID principles as design heuristics rather than rigid rules. The most important shift was favouring composition over inheritance and programming to interfaces, so behaviour can vary without modifying existing classes (Open/Closed Principle).

Practical evidence: SmartDesk’s domain layer depends only on abstract base classes (Python’s abc module) such as Classifier and PricingStrategy, with concrete implementations injected through constructors. When an early TicketManager class accumulated too many responsibilities, I refactored it into smaller single-responsibility classes for validation, routing and persistence.

1.3 Design patterns for reusable, maintainable and flexible code

Patterns gave me a shared vocabulary for recurring problems, and I learned to select them by the design force they resolve rather than by familiarity.

Advanced design patterns (practical application)

  • Strategy – runtime behavioural flexibility: triage and pricing algorithms are selected at runtime from client configuration, removing conditional logic scattered across the code.

  • Decorator – separation of concerns: logging, authorisation and timing wrap the core service without polluting business logic.

  • Visitor – extensibility: new reports are added as new visitor classes while the ticket and asset hierarchy remains stable.

  • Abstract Factory – scalability: whole families of AI services (classifier and summariser) can be switched between a cloud provider and a locally hosted model by changing one factory.

AI-oriented OO patterns (conceptual awareness)

I was also introduced to AI-inspired architectural patterns. A Model Registry manages the lifecycle of machine-learning models: versioning, metadata, approval stages and rollback. A Feature Store centralises feature definitions so a feature such as “tickets raised by this client in 30 days” is computed identically for training and inference, avoiding training–serving skew. I did not build production versions, but I modelled a lightweight ModelRegistry class in SmartDesk that maps model names and versions to classifier objects, which made the link between OO design and MLOps concrete.

1.4 Architectures for large-scale, secure and robust systems

I learned to structure systems in layers (presentation, application, domain, infrastructure) with dependencies pointing inward, so core logic is independent of frameworks and vendors. Robustness came from defensive design: fail-safe defaults, timeouts and retries around external calls, and fallbacks when a dependency is unavailable.

Practical evidence: SmartDesk follows this layered structure. If the AI provider times out, the router falls back to the rule-based triage strategy, so the service degrades gracefully rather than failing. Role-based access is enforced by a decorator at the application boundary.

1.5 Solutions adaptable for AI models and efficient for data science

I learned that AI-readiness is largely an interface problem: if models sit behind stable abstractions they can be retrained, versioned or replaced without destabilising the system. For data efficiency I used generators to stream ticket records and kept data transformation separate from model logic.

Practical evidence: every SmartDesk model implements a common predict() interface and is retrieved from the registry by version, enabling side-by-side comparison of two classifiers. Visitor-based reports export to pandas DataFrames for analysis.
