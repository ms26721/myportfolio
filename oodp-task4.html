Task 4: Professional Development Plan

Advanced Object-Oriented Design & Programming · Capstone Project: End of Module Reflective Portfolio

4.1 Introduction

This reflection follows Gibbs’ Reflective Cycle (Gibbs, 1988): description, feelings, evaluation, analysis, conclusion and action plan. Within the analysis, I draw on Kolb’s experiential learning cycle (Kolb, 1984) to explain how my understanding grew through practice rather than reading alone. It covers the academic and employability skills I developed during the module and its Capstone Project (SmartDesk).

4.2 Description and feelings

I began this module with no prior experience of object-oriented programming. Python was also new to me, so I was learning a language and a programming paradigm at the same time. The module moved quickly from core principles to design patterns, concurrency, secure coding and testing. It ended with the SmartDesk Capstone Project, which brought these topics together in one system.

My first feeling was uncertainty. Concepts such as polymorphism and abstraction seemed theoretical when I met them in reading, and Python syntax slowed me down before I could focus on design. I worried that I would understand patterns on paper but not know when to use them.

That feeling changed as the seminars progressed. Seeing a pattern applied to a concrete problem made the theory meaningful. By the end of the module, the main feeling was satisfaction: the separate topics fitted together into a single, working architecture that I could explain.

4.3 Evaluation

The strongest part of the module was the seminars. They were well prepared, and the instructor explained concepts clearly. Most importantly, he showed the anatomy of the final submission early, so I understood what a complete project needed before I started building it. This gave me a map for a large amount of unfamiliar material.

The main difficulty was the double learning curve. Time spent on Python syntax was time not spent on design, and early on I sometimes understood why a pattern existed but could not yet write it confidently. Balancing the module with long working hours made this harder, which I discuss under time management below.

4.4 Analysis: academic skills

Critical thinking and problem-solving

Kolb’s cycle reflects the development of my thinking: seminar exercises provided concrete experience, reviewing them supported reflective observation, Gamma et al. (1994) introduced the abstract concepts, and the Capstone enabled active experimentation. The main shift was learning to identify what was likely to change before selecting a design pattern.

In SmartDesk, triage and pricing rules varied across client contracts and were expected to evolve as service requirements changed. I therefore used the Strategy pattern to place these behaviours behind a common interface, allowing individual rules to be replaced or extended without altering the wider system. Reporting requirements also changed frequently, whereas the underlying ticket and device structure remained comparatively stable. This made the Visitor pattern a suitable choice because it allowed new reporting operations to be introduced without adding reporting logic to the domain classes, despite the additional effort required when introducing new element types. Through these decisions, I learned that design patterns should not be applied simply because they are familiar; each pattern must address a clearly identified source of change and provide benefits that justify its added complexity.

Ethical considerations in AI-driven design

The module showed me that ethics is partly a design decision. If biased weights sit in a base class, every subclass inherits them, and the bias spreads quietly through the hierarchy (Mehrabi et al., 2021). Tight coupling to a model also hides its behaviour, creating “black box” components that are hard to test or audit (Sculley et al., 2015).

I responded through design. Every SmartDesk classifier exposes an explain() method returning the label, confidence and key features, models are versioned in a ModelRegistry and an audit-logging decorator records each decision. Clean interfaces made the system testable with mocks, which is also what makes it auditable.

Research and self-study

Beyond the seminars, I used the module readings, the OWASP guidance on secure coding (OWASP Foundation, 2021) and the Python documentation. The reading that most changed my thinking was Sculley et al. (2015) on hidden technical debt in machine-learning systems. It led me to keep SmartDesk’s models behind stable interfaces and a lightweight model registry.

I also used an AI assistant to support the development and organisation of the Capstone code. However, my learning came from examining, running and questioning each component until I could explain it independently. This reinforced a key lesson from the module: AI tools can improve efficiency, but engineering judgement must remain with the developer.

4.5 Analysis: employability skills

Time management

Time management was my main challenge. Long working hours left limited, often tired, study time, while Python and OOP both demanded steady practice. I split the Capstone into milestones tracked on a Kanban board, and starting testing early prevented a last-minute crunch. The lesson I take forward is to plan the hardest learning for the times I am most alert, and to start large tasks early rather than relying on a final push.

Communication and literacy

Writing about the Capstone forced me to explain design choices in plain language, not just implement them. Being able to say why a pattern was chosen, and what it costs, is a skill I can use directly with clients and colleagues. UML class and sequence diagrams helped me explain SmartDesk’s structure in discussion forums, and in peer code review I learned to justify trade-offs such as the debugging cost of deep decorator chains.

Resilience and interpersonal skills

Learning two new things at once while working full time required persistence. Early confusion was uncomfortable, but I learned that it was a normal stage of learning rather than a sign of failure. Setbacks such as the race condition in the ticket ID generator taught me to reproduce a problem before fixing it. Clear teaching and the structure of the seminars helped me keep going when progress felt slow.

4.6 Conclusion and action plan

I started the module new to both OOP and Python, and finished able to choose, justify and critique design patterns in a working system. The most important change is in how I think: I now design for change, testability and accountability, not just for code that runs.

Area for improvement Action Evidence of progress
Python fluency Regular coding practice; Python Institute PCAP certification Certification passed
Pattern judgement Study Freeman and Robson (2020); refactor one small project per pattern Refactored projects on GitHub
Testing intelligent systems Extend mocking and property-based testing to a new AI-dependent project Test suite with documented edge cases
Time management Fixed weekly study blocks planned around work shifts Coursework started at least two weeks before deadlines

Conclusion

This module moved me from knowing patterns and principles to applying them with judgement. SmartDesk demonstrated how secure, layered, pattern-based design and disciplined testing produce systems that are robust today and ready for AI tomorrow, while my reflections on trade-offs and ethics reminded me that good design is ultimately about responsible decisions, not just elegant code.
